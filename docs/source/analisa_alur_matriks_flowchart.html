1. Scope Analisa Codebase

Berdasarkan penelusuran struktur direktori dan source code pada workspace c:\laragon\www\audit, aplikasi ini merupakan sistem web enterprise untuk pelaksanaan dan pelaporan Audit Internal Sistem Manajemen Keselamatan Pertambangan (SMKP Minerba) berbasis Kepmen ESDM No. 1827 K/30/MEM/2018.

1.3 Pola Arsitektur Eksekusi

Alur data mengikuti pola Controller-Driven with Eloquent ORM & Database Transactions. Tidak ditemukan service layer terpisah (logic terkapsulasi dalam controller dan model helper). Seluruh operasi update kriteria, persistensi file lampiran, dan triggering PICA dieksekusi secara atomik dalam DB::transaction.

2. Deskripsi Alur Step-by-Step SMKP MINERBA SYSTEM

2. Deskripsi Alur Eksekusi Terperinci

Penelusuran alur eksekusi dari interaksi antarmuka pengguna hingga persistensi basis data dan pencatatan audit trail:

  • 1
    User Interaction & Input Data (Layer: User / Browser)

    Auditor membuka matriks penilaian sesi audit, mengisi skor nilai kriteria (0–4), mencentang checkbox N/A jika kriteria tidak relevan, menuliskan catatan temuan, serta melampirkan berkas bukti audit.

  • 2
    Client-Side Calculation & Form Submission (Layer: Frontend Blade/JS)

    Script JavaScript menghitung total skor per elemen secara dinamis di antarmuka. Saat tombol "Simpan" diklik, form di-submit via HTTP POST (multipart/form-data) menyertakan token proteksi CSRF.

  • 3
    Security & RBAC Validation (Layer: Middleware Stack)

    Permintaan disaring bertingkat: VerifyCsrfToken (menolak jika token mismatch/419), Authenticate (menolak jika session expired/401), dan CheckRole:admin (menolak jika role tidak sesuai/403).

  • 4
    State Guard & Input Validation (Layer: Controller)

    Controller memeriksa status sesi. Jika status 'selesai', request di-abort (403). Selanjutnya aturan validasi dieksekusi untuk memastikan tipe numerik nilai, status boolean N/A, dan validitas MIME type file (PDF, JPG, PNG).

  • 5
    Atomic Transaction & File Storage (Layer: Database & Storage)

    Controller membuka DB::beginTransaction(). File lampiran diunggah ke storage/app/public/lampiran/. Field audit_details diperbarui (skor, nilai maks, catatan bullet, dan array path lampiran).

  • 6
    Automated PICA Triggering & Cleanup (Layer: Business Logic)

    Jika !is_na && nilai < nilai_maks, sistem otomatis membuat temuan PICA baru (status: open, kategori: minor). Jika nilai dinaikkan ke nilai maks dan belum ada akar masalah, draft PICA dihapus.

  • 7
    Sub-Elemen < 50% Auto-Classification (Layer: Business Logic)

    Sistem menghitung total kepatuhan sub-elemen terkait. Jika persentase kepatuhan < 50%, seluruh temuan PICA pada sub-elemen tersebut otomatis ditingkatkan keparahannya menjadi Kategori Mayor.

  • 8
    Session Recalculation, Logging & Commit (Layer: Controller & DB)

    Method $sesi->hitungSkorAkhir() dijalankan untuk mengagregasi skor total 7 Elemen. Catatan audit trail disimpan ke audit_logs, transaksi di-commit, dan user dialihkan kembali dengan status sukses.

5. Catatan Temuan & Asumsi SMKP MINERBA SYSTEM

5. Catatan Temuan & Asumsi Analisa

5.1 Catatan Temuan Teknis & Rekomendasi

⚠️ 1. Proteksi Hapus Draft PICA (Auditee Data Preservation)

Implementasi kode memeriksa apakah akar_masalah == null && tindakan_koreksi == null sebelum menghapus PICA. Hal ini mencegah hilangnya rencana tindakan korektif yang telah disusun oleh Auditee jika Auditor melakukan penyesuaian nilai kriteria di kemudian hari.

💡 2. Kepatuhan Regulasi ESDM (Auto-Escalation Sub-Elemen < 50%)

Logika bisnis menerapkan aturan Kepmen ESDM No. 1827 K/30/MEM/2018 Lampiran II secara otomatis: jika akumulasi nilai pada suatu Sub-Elemen berada di bawah 50% dari total nilai maksimumnya, seluruh temuan kriteria di sub-elemen tersebut otomatis ditingkatkan keparahannya menjadi temuan Kategori Mayor.

📁 3. Manajemen Penyimpanan File Lampiran

Setiap upload lampiran baru disimpan ke dalam array JSON lampirans pada tabel audit_details tanpa menghapus file lama. Hal ini menjaga riwayat bukti audit (audit evidence retention), namun disk storage disarankan dibersihkan melalui cron task arsip jika sesi audit telah melewati masa retensi aktif.

5.2 Asumsi yang Diambil dalam Analisa

Asumsi Rasionalisasi Berdasarkan Codebase
Status Sesi Aktif Diasumsikan pengujian dilakukan pada sesi audit berstatus draft atau berjalan. Sesi berstatus selesai akan diblokir oleh controller guard.
Arsitektur Monolitik Aplikasi menggunakan arsitektur Laravel Monolith dengan rendering Blade. Tidak ditemukan dependensi microservices atau Elasticsearch eksternal pada modul penilaian ini.
Kekuatan Transaksi Atomik Penggunaan DB::beginTransaction() dan DB::commit() menjamin integritas data multi-kriteria secara menyeluruh terhadap kegagalan jaringan atau server.
